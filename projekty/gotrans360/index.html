01

IDEA / ZASTOSOWANIE

Od potrzeby do produktu.

POTRZEBA

Problem

Ręczne planowanie przewozów i rozproszone dane o trasach, pojazdach i zapotrzebowaniu utrudniają wykorzystanie dostępnych miejsc i ograniczanie pustych przebiegów.

Dla kogo

  • Przewoźnicy
  • Dyspozytorzy
  • Docelowo pasażerowie i nadawcy przesyłek
ODPOWIEDŹ

Rozwiązanie

Monorepo rozdziela dwa interfejsy Next.js, API Node.js, modele Prisma i moduł dopasowania. To fundament produktu transportowego, z jawnymi granicami między działającym kodem a demonstracyjnymi ekranami.

Dlaczego powstał

Sprawdzić wspólny model tras i floty oraz dopasowanie zapotrzebowania do przejazdów przed uruchomieniem pełnej usługi przewozowej.

02

ARCHITEKTURA / POŁĄCZENIA

Technologia pod powierzchnią.

  1. 01

    Dwa interfejsy Next.js: dyspozytor i pasażer.

  2. 02

    API Node.js i Prisma; frontend nie korzysta jeszcze z całości API.

  3. 03

    Osobny moduł heurystyk i adapter Valhalla.

03

FUNKCJE / POTWIERDZONY ZAKRES

Zaprojektowane do działania.

  • Interfejs dyspozytora z ekranami floty, tras i dopasowania; dane operacyjne tych widoków są demonstracyjne. [1]
  • Formularz wyszukiwania i rezerwacji pasażera; obecny frontend nie realizuje rezerwacji przez backend. [1]
  • Sesja cookie i role w aplikacji dyspozytora oraz weryfikacja tokenu w osobnym API. [1]
  • Endpointy przejazdów, pojazdów i przewoźników oraz modele Prisma; integracja z frontendami pozostaje otwarta. [1]
  • Heurystyka dopasowania według miejsc, odległości objazdu i szacowanego zysku, oparta o Haversine. [1]
  • Adapter zapytań trasowania do Valhalla, przygotowany jako kod integracyjny. [1]
Wyniki i granice weryfikacji
  • Raport z sierpnia 2026 potwierdza odczyt 12 567 syntetycznych tras przez bazę i API w izolowanym teście. Wynik nie oznacza obsłużonych przewozów ani ruchu produkcyjnego.
  • Historyczny benchmark trzykrotnie potwierdził dwie propozycje Smart Match dla dokładnie dwóch demonstracyjnych tras i dwóch zgłoszeń.
  • Audyt kodu rozróżnia API danych, ekrany demonstracyjne i planowany proces rezerwacji. Nie uruchamiano ponownie produktu podczas audytu portfolio.

ROZWÓJ / OTWARTE KIERUNKI

Następne kroki.

Fundament MVP transportowego · Lokalne repozytorium i historyczne buildy; brak potwierdzonego wdrożenia.

Do potwierdzenia lub ukończenia

  • Połączyć wyszukiwanie, rezerwację i panel z autoryzowanym backendem.
  • Zamknąć przegląd bezpieczeństwa, izolacji danych i migracji bazy.
  • Zastąpić demonstracyjne dane rzeczywistymi przepływami i wykonać E2E.
  • Aplikacja kierowcy pozostaje szkieletem.

Planowane kierunki

  • Połączenie paneli WWW z pełnym API operacyjnym
  • Rzeczywiste wyszukiwanie i cykl rezerwacji
  • Docelowa obsługa przesyłek, płatności i telemetrii
  • Dalszy odbiór jakości oraz przygotowanie wdrożenia
